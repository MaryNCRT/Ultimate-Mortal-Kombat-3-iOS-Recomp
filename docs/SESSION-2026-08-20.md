## Why the runtime and not `lime/common`

`OUTPUT/` is not in the repository — no `UMK3.armv6`, no `UMK3.armv7`, no
`functions.txt` — so the 63 remaining `lime/common` functions, which are the
project's real bottleneck, cannot be touched from a clone alone. Neither can
the game data: no `.skin`, `.bones`, `.skinanim` or `.meshset` files exist here
and none were created inside the tree.

So this session took the two items from [HANDOFF.md](HANDOFF.md) §2 that need
neither: the SDL2 backend, and `tools/pose.py`'s skinning moved into C.

**If you can supply the armv6/armv7 slice** (or a build of `OUTPUT/`), the
decompilation route reopens immediately and it should take priority over
anything below.

## 1. The SDL2 backend — [PR #15](../../pull/15)

The vertical slice was Windows-only for a structural reason, not an accidental
one: `runtime/main.c` included `windows.h` directly, `win32_gl.c` was the only
backend, and CMake `message(FATAL_ERROR)`'d anywhere else.

- `runtime/platform/gl.h` — one place that knows where the GL headers live.
- `runtime/platform/sdl_gl.c` — the same six-function `platform.h` contract.
- CMake picks `win32` on Windows and `sdl2` everywhere else;
  `-DUMK3_BACKEND=sdl2` forces it on Windows too.

The context is requested as **compatibility, not core**. The slice draws
through fixed-function client arrays, and a core context gives a black window
with no error.

Verified on Linux against a generated `.meshset`: window, context, geometry,
lighting, rotation, Esc.

## 2. Native skinning — this branch

`tools/pose.py` could pose a character and `runtime/` could not. That gap is
now closed.

| | |
|---|---|
| `runtime/lime/skin.h` / `.c` | parsers for `.bones`, `.skinanim`, `.skin`; matrix palette; vertex posing |
| `runtime/character.c` | the viewer — `umk3 <NAME>.skin [--frame N \| --idle]` |

`runtime/main.c` dispatches on the extension, so the `.meshset` path is
untouched.

The arithmetic follows [SKIN-FORMAT.md](SKIN-FORMAT.md) and
`decomp/lime/RenderSkinned.c`, and the parts that are easy to get wrong are the
same ones the Python found the hard way:

- the palette is built **depth-first**, and animation quaternions are consumed
  in **visitation order**, not by bone index;
- the root translation comes from the **animation frame**, not from the
  `.bones` root offset;
- quaternions are `(x, y, z, w)`, `w` last;
- the vectors in a `.skin` matrix are **already weighted** — position is
  `Σ (A[i]·M3x3 + w[i]·T)`, normal is `Σ (B[i]·M3x3)`;
- `0xFF` in a packed index byte is an empty influence slot;
- lighting is the engine's monochrome `LightVert`, so `R = G = B`.

The variants from rule 5 in the handoff are all handled: 24-byte ROBO bone
records, ROBO's bare `.skin` block with no leading count, and SINDEL's 16-byte
`.skinanim` header whose frame count disagrees with the file. Frame size is
read from the animation header, never derived from the matching `.bones` —
ROBO's counts do not match.

### How it was verified without game data

A generator outside the tree (`/home/ubuntu/scratch/make_char.py`, deliberately
not committed) writes a synthetic skinned tube to the documented spec: 9 bones
in a chain, 90 vertices, 160 triangles, 60 frames, two-bone influences, and a
child in slot 1 with slot 0 empty, because real files do that.

Then `umk3 --dump` is diffed against `tools/pose.py` vertex by vertex:

```
frame  0: 90 vertices, max |C - pose.py| = 0.0000548
frame  7: 90 vertices, max |C - pose.py| = 0.0000565
...
worst divergence across every frame: 0.0000596
```

That residual is the four-decimal print width, not the maths. The ROBO-shaped
and SINDEL-shaped rewrites of the same data produce identical numbers through
the fallback paths, which is what makes them worth having.

The window was then checked on screen: the tube bends along the chain, the wave
travels down it frame to frame, the shading is the engine's, Esc quits, and the
`.meshset` path still loads and draws.

**This is not verification against the game.** It proves the C agrees with the
Python and that both agree with the documented format. The first real character
file will be the actual test — that is the first thing to run when the data is
available.

## Not done / next

1. **`lime/common`, 63 functions.** Still the bottleneck, still blocked on
   `OUTPUT/`.
2. **Morph / shape keys.** Documented, not played back on either side.
3. **The renderer is still fixed-function.** Fine for a slice, not the target.
4. **Textures for characters** are looked up beside the `.skin`; the naming
   convention has not been exercised against real assets.
5. `.lighting` remains undecoded — if it is the prelight bake it appears to be,
   `LightVert` is the fallback path and most characters are lit from the table.

## Environment

Building the slice on Linux needs `build-essential cmake pkg-config
libsdl2-dev libgl1-mesa-dev`. That is now in the repository's Devin blueprint,
so future sessions come up ready.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/umk3 NAME.skin --idle       # stance
./build/umk3 NAME.skin              # play the clip
./build/umk3 NAME.skin --dump       # every posed vertex, for diffing
```
